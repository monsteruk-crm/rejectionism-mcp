## Fixed implementation decisions
### File organization
Use `lib/campaign/` for server-only business logic: `schemas.ts`, `results.ts`, `test-mode.ts`, `activity.ts`, `work-items.ts`, `canon.ts`, `decisions.ts`, `assets.ts`, `websites.ts`, `contacts.ts`, `content.ts`, `status.ts`, and `seed.ts`. Keep this domain-specific; do not invent a generic repository framework. Use `lib/mcp/campaign-tools.ts` and `lib/mcp/tool-result.ts` for thin registration/serialization adapters. Existing bootstrap tools may move into `lib/mcp/bootstrap-tools.ts` so both endpoints reuse them.
Use `app/admin/actions.ts` for Server Actions and `app/admin/_components/` for shared forms, result messages, navigation, and badges. Create dashboard and entity pages listed below. Keep Prisma and server-only modules out of Client Components. Share only serializable types/constants or independent client-safe form schemas with the browser.
### Test-mode boundary
`isTestModeEnabled()` must evaluate `process.env.UNAUTHENTICATED_TEST_MODE === "true"` at call time. Never use truthiness, case folding, a browser variable, or a value captured at module import. Gate every domain service, including seed and every mutation, before acquiring Prisma. A caller cannot bypass the gate with an input flag.
Choose the conservative interpretation of fail-closed: when disabled, no campaign reads or writes are served. MCP may still advertise tools; campaign calls return `TEST_MODE_DISABLED`. Preserve the existing harmless bootstrap diagnostics. `/admin` displays only the disabled notice; individual page reads and Server Actions must also enforce the service gate, because a layout alone is not a security boundary. Health remains available. Test missing, empty, `false`, `TRUE`, and ` true ` values.
When enabled, show `UNAUTHENTICATED TEST SYSTEM — DO NOT STORE PRIVATE OR SENSITIVE DATA` on every admin page and in README. Use only non-sensitive test data; do not seed private contacts, the Pope's private identity, credentials, or rejection letters. This switch is not authentication or authorization. Authentication/authorization is milestone one after MVP.
### Input and result conventions
All public service functions accept unknown input and parse strict Zod schemas. Nested objects must also reject extra keys. Allow-list update fields; reject empty patches. Titles/names/keys max 200 characters, long text max 20,000, URLs max 2,048, IDs max 100, search max 200; trim text and reject whitespace-only required values. Priority is integer 0–100; larger means earlier. Versions are positive integers starting at 1.
Use absolute HTTP/HTTPS URLs only, nullable optional dates/URLs/notes, valid ISO timestamps at the transport boundary, and JSON-safe ISO strings in DTOs. Never fetch caller-supplied URLs. Dates on forms need explicit UTC conversion. Treat omitted update fields as unchanged and explicit null as cleared. Validate domains as lowercase hostnames without scheme, path, credentials, or port. Do not render arbitrary HTML/Markdown from database text.
Service result union: `{ ok: true, data }` or `{ ok: false, error: { code, message, fieldErrors? } }`. Codes: `VALIDATION_ERROR`, `NOT_FOUND`, `VERSION_CONFLICT`, `TEST_MODE_DISABLED`, `ALREADY_EXISTS`, `DATABASE_UNAVAILABLE`, `INTERNAL_ERROR`. Keep messages sanitized; never include Prisma errors, connection strings, stack traces, environment values, or raw inputs in outputs/logs.
Read lists use bounded `limit` (default 50, max 100) and nonnegative `offset` (max 10,000), return `{ items, total, limit, offset }`, and deterministic ordering. Admin adds basic pagination. Activity defaults to 20/max 100. DTOs expose versions needed for later writes.

## Phase 2 — Schema and authored migration
Update `prisma/schema.prisma`, add a new named migration such as `campaign_os`, update `prisma7.config.ts` seed configuration, and regenerate the client. Read the relevant Prisma CLI/client skills before implementation; this is existing Prisma 7, not an init/Composer/Prisma 8 task.
Use string IDs with `@default(cuid())` for campaign records, `createdAt @default(now())`, `updatedAt @updatedAt` wherever specified, `version Int @default(1)` on mutable versioned entities, and nullable optional fields. Required descriptions can default to empty text. Add all fields named in boot; these clarifications close its gaps:
- `WorkItem`: required title, description, status default `BACKLOG`, priority default 0; nullable dueDate, blockedReason, evidenceUrl; additionally persist nullable `completionNote`. Completion notes must not exist only in transient tool arguments.
- `CanonEntry`: unique immutable key; required value/category; nullable notes; versioned.
- `Decision`: subject/decision/rationale, nullable `supersedesId` with self-relation and restrictive deletion; default decidedAt now. Decisions are immutable and append-only, so no versioned edit endpoint. Make non-null supersedesId unique: an earlier decision has at most one direct successor. Expose successor IDs so old decisions remain visible.
- `Asset`: required name/kind/status; nullable sourceFilename/url/notes; versioned. Kind is bounded text rather than an invented closed taxonomy.
- `Website`: required name/unique normalized domain/purpose/status; nullable repositoryUrl/deploymentUrl/notes; versioned. Domain is immutable in the MVP edit flow.
- `Contact`: required name; organization/role/notes nullable, email optional and validated, status bounded text default `PROSPECT`. Add version because contact edits must follow the same concurrency contract. No private contact seed.
- `ContentItem`: required title/format/channel; nullable scheduledFor/publishedUrl/notes; versioned. Add enum `DRAFT`, `SCHEDULED`, `PUBLISHED`, default `DRAFT`. Require scheduledFor for SCHEDULED and publishedUrl for PUBLISHED.
- `Activity`: entityType/entityId/action/summary, optional JSON metadata, createdAt; append-only, no public update/delete API. Use an entity-type enum covering the seven domain entity types.
Use boot's exact WorkItem, Asset, and Website status enums. Add indexes on WorkItem status/priority, dueDate; CanonEntry category; Asset status/kind; ContentItem status/scheduledFor; Decision decidedAt; Activity createdAt and entityType/entityId/createdAt. Use stable secondary ordering by ID for ties.
Inspect generated SQL: only additive campaign tables/enums/indexes/relations; no dropping User, truncation, or rewritten history. Create/apply the migration only against an explicitly approved disposable/local PostgreSQL target. If no such target is available, implement source and prepare/review migration SQL using Prisma's supported diff tooling; report application/integration verification as blocked. Never use db push as migration acceptance or accept a reset prompt.
## Phase 3 — Shared services, atomic audit, and concurrency
Implement services before UI/MCP. Domain modules import `server-only`; keep the reusable Prisma factory usable by the trusted seed CLI. In Vitest, alias the marker to a test-only empty module; never bypass it in production. The seed command can run Node with the `react-server` condition when importing server-only services; verify this CLI path explicitly.
For a versioned update, perform one Prisma interactive transaction: load the record, distinguish missing from stale version, validate the merged final state, update with an atomic predicate `{ id, version: expectedVersion }` (e.g. updateMany), increment version, require affected count 1, create Activity using the transaction client, and return the updated DTO. A pre-read version check followed by an unconditional update is forbidden. If the conditional update loses a race, abort with VERSION_CONFLICT. Catch/map failures outside the transaction callback; throwing is required to roll back earlier writes. Do not silently retry a user's stale patch.
Every successful create/update creates Activity in the same transaction. A stale, invalid, disabled, failed-audit, or missing-record mutation changes neither entity nor Activity. Activity metadata contains only source (`admin`, `mcp`, `seed` set by trusted adapters), changed field names, versions, and relevant decision IDs/completion note; do not copy entire records or sensitive values. Seed no-ops make no Activity/version changes.
WorkItem completion validates the resulting record on both create and update: DONE requires a valid evidenceUrl OR trimmed nonempty persisted completionNote. Clearing the final evidence from an already-DONE item must also fail. BLOCKED requires a nonempty blockedReason; leaving BLOCKED clears obsolete blockedReason unless explicitly retained for a documented reason. All listed statuses can otherwise transition; do not invent a rigid workflow.
`recordDecision` creates the immutable decision and optional explicit canon mutation in one transaction, with Activity for each changed entity. Validate the superseded decision exists and has no successor. Superseding never overwrites/deletes its text. Unique supersedesId prevents concurrent branching; return VERSION_CONFLICT for a loser. `updateCanon` omitted means no canon changes. When present, accept either create-new-key mode (must not exist), or update-existing-key mode with expectedVersion. A canon conflict rolls back the decision and all audit entries. No implicit slogan/name extraction.
Provide create/update/read services for work items, canon, assets, websites, contacts, content; record/list decisions; read activity; get campaign status. Contacts need only a small list/create/edit admin screen, not new MCP tools. No entity deletion, bulk writes, arbitrary SQL, file upload, or URL-fetch services.
`getCampaignStatus` returns all five status counts including zeros; bounded inProgress, blocked, missingAssets, website summary, recent decisions (10), latest activity (20), and next three NEXT items ordered priority descending then createdAt/ID ascending. Include totals/truncation flags for bounded collections so omissions are not mistaken for absence. Use one shared result for dashboard and MCP. Do not treat a planned redirect as live or infer work completion from wording.
